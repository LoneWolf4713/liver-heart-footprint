TOTAL: >100 lab-measured data points for fried South Asian foods across 6+ sources (vs 8 before).

KEY FINDING: the SAME dish varies 3-5x across sources (samosa: 6.7-8.7 [FAME, Joshee], 9.3 retail, 17.3 takeaway, 29.2-29.6 street [Gupta], 31.5 homemade lamb deep-fried [CoFID]; bread pakora 18.1 / 26.4 / 47.6; mathri 21.8 / 38.5 / 57.2; bhatura 10.0 / 19.6). Variation comes from recipe, vendor, oil, frying practice AND measurement method.
IMPLICATION: a single "true" samosa fat value does not exist. Frying model must output an evidence-based RANGE/distribution (by category x setting home/street/restaurant x method), not a point estimate. Honest validation = does the predicted range cover held-out lab measurements (coverage) + error of the median. The compiled dataset itself ("first open compilation of lab-measured fat in Indian fried foods") is a contribution.

## B. Can the professor's food pairing drive swaps?
- Food pairing (FlavorDB shared flavour molecules) measures which ingredients GO TOGETHER (complements), not which REPLACE each other.
- [V] Teng, Lin & Adamic 2012 (WebSci; arXiv 1111.3919; allrecipes): COMPLEMENT network (co-occurrence) splits into savory/sweet; SUBSTITUTE network (mined from users' suggested modifications in reviews) forms communities of FUNCTIONALLY EQUIVALENT ingredients and captures preference for HEALTHIER variants.
- [V] Shirai et al. 2020 (Frontiers in AI, FoodKG substitution): ingredients used together (garlic + olive oil) are similar but NOT substitutable; dissimilar items can be good substitutes (potato vs cauliflower); flavour molecules are hard to relate to the flavour experience in recipes; use recipe-context similarity + embeddings.
- [V] 2025 review (Foods, PMC12651232): "Flavor compatibility ... cannot be determined by molecular similarity alone"; substitution must match function + sensory + nutrition + culture.
- [V, from file 25/26] FlavorDB coverage of Indian fats/sweeteners is sparse (12/26; ghee 1 molecule).
CONCLUSION: using food-pairing similarity directly as "substitutability" would be conceptually WRONG. Correct use of the professor's work: a FIT CHECK (does the substitute pair well with the rest of the dish's ingredients?), not the swap generator.
Better swap generator (data-driven, not from scratch):
 (1) context similarity from our recipe corpus: substitutes appear in the same "slot" of the same dish across recipes but rarely together (Teng/Shirai logic);
 (2) MINE AUTHOR-STATED SUBSTITUTIONS from Indian recipe pages (FAQ/notes: e.g., Hebbar's "alternative to cream, you can use curd"; VRoI "Can I use curd instead of cream? ... 2 tbsp whole milk yogurt"; vegan swaps) -> an Indian substitute network (like Teng's from reviews);
 (3) quantity-reduction rule from the recipe distribution (lightest 25% of real recipes);
 (4) FlavorDB pairing as a secondary fit check where coverage exists;
 (5) rank by load cut x authenticity.

## Q (user, 2026-09-30): why collect cooked-food data at all if we infer from ingredients?
Answer logged: ingredient inference IS the main engine (non-fried dishes: fat and sugar are conserved in cooking, so summing ingredients works; water loss only changes per-100 g concentration). Cooked/lab data is needed for exactly two things: (1) DEEP/SHALLOW FRYING: the recipe states oil in the pan ("oil for deep frying"), never oil absorbed by the food, so the key liver number is absent from the ingredient list and must come from measured uptake (e.g., Tarla Dalal samosa 256 kcal omits absorbed oil; measured samosas 9-31 g fat/100 g); (2) VALIDATION: proving ingredient-sum estimates are right (Chen 2009: calculated values exceeded analysed for most nutrients; macros closest). Minor: some oil stays in the pan / is discarded (tadka, bhuna) -> small correction, report as range.
